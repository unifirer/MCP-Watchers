================================================================================
FIX: grepai watcher not tracking file changes
================================================================================
Date/Time : 2026-07-09 (Thu) ~17:40 local
File      : ###launch watcher for grepai.ps1
Author    : opencode (verified via empirical change-tracking test)

--------------------------------------------------------------------------------
SYMPTOM
--------------------------------------------------------------------------------
The grepai file watcher appeared to be "not working." Symptoms observed:
  - `grepai watch --status` reported "not running" even though a
    `grepai.exe watch` process was alive (PID 45404).
  - `grepai watch --stop` reported "No background watcher is running" yet the
    process had to be force-killed.
  - Creating / modifying files did NOT update the index: `.grepai/index.gob`
    LastWriteTime stayed static, and newly created files never appeared in
    `grepai search` results.
  - The running watch process was idle (CPU delta ~0.05s over 6s, 92MB static
    working set) after completing its initial scan.

--------------------------------------------------------------------------------
ROOT CAUSE
--------------------------------------------------------------------------------
The launch script started the watcher in FOREGROUND mode by spawning a new
console window:

    $cmdStr = '...; grepai watch; if ($LASTEXITCODE -ne 0) {...}'
    Start-Process -FilePath "powershell.exe" -ArgumentList "-NoProfile","-Command",$cmdStr

This bypasses grepai's own background-process registry, so:
  1. grepai's native `--status` / `--stop` commands are blind to the process.
  2. The foreground instance does not process filesystem events (it goes idle
     after the initial scan and stops tracking changes).

A background-mode instance (`grepai watch --background`) correctly registers
with grepai and reliably tracks both new files and modifications.

--------------------------------------------------------------------------------
FIX
--------------------------------------------------------------------------------
Replaced the foreground `Start-Process` spawn (lines ~132-135) with a direct
background launch plus exit-code error handling:

    Write-Host "Starting grepai watch (background)..."
    grepai watch --background
    if ($LASTEXITCODE -ne 0) {
        Write-Error "grepai watch --background exited with code $LASTEXITCODE..."
        Write-Host "Press Enter to exit..."; $null = Read-Host; exit 1
    }

The existing `grepai watch --status` guard (top of script) now works as
intended, and the CIM fallback check remains as a safety net.

--------------------------------------------------------------------------------
VERIFICATION (empirical, before vs after)
--------------------------------------------------------------------------------
BEFORE (foreground launch):
  - index.gob mtime unchanged after creating a new file (VAD_WATCH_TEST_zzz.md).
  - New file absent from `grepai search` results (top scores ~0.51, unrelated).
  - index.gob mtime unchanged after modifying README.md.

AFTER (background launch, PID 49796 via the actual launch script):
  - index.gob mtime advanced 17:39:46 -> 17:40:17 after creating a new file.
  - New file VAD_WATCH_TEST_final.md appeared in `grepai search` results
    (score 0.523, top-10).
  - `grepai watch --status` now correctly reports "Status: running (PID 49796)".
  - `grepai watch --stop` now correctly stops the watcher.
  - Modification of an existing file (README.md) also advanced index.gob mtime.

All test artifacts (VAD_WATCH_TEST_*.md and README.md markers) were removed
after each test; repository left clean.

--------------------------------------------------------------------------------
RECOMMENDATION / FOLLOW-UP
--------------------------------------------------------------------------------
- Keep the foreground-spawn pattern out of this script; only `grepai watch
  --background` is tracked and actively watches.
- Note: the earlier (Aug-07) grepai-worktree log also contained a Go
  "fatal error: out of memory" (errno=1455) crash during a prior watch run.
  If OOM recurs, consider reducing embedder.parallelism (currently 4) or the
  RPG batch size in .grepai/config.yaml. Not related to this fix.
