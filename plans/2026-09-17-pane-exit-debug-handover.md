## 1. Executive Summary

An investigation was conducted to determine why Windows Terminal panes spawned by ###1.watchers_for_memtrace_grepai_graphenium_graphify-rs_repowise.ps1 terminate automatically after several hours of operation.

The investigation mapped the complete lifecycle across:
1. Launcher Controller: ###1.watchers_...ps1 (controller loop, heartbeat scanner, supervisor jobs).
2. Pane Tailer Generation: Modules/watcher_pane_scripts.ps1 (New-WatcherPaneScript).
3. Daemon Lifecycles: grepai supervisor & idle reaper, graphify-rs parent-death guard, graphenium internal thread job.
4. Heartbeat Protocol: Pane heartbeat files under C:\Temp\vad-watchers\panes\hb\*.hb and the 8-second global controller timeout.

## 2. Root Cause Analysis

Four distinct failure mechanisms combine to cause the panes to close prematurely:

### Root Cause 1: grepai Idle TTL Reap Cascades to Pane Exit (Primary)
- Mechanism: Modules/watcher_job_helpers.ps1 defines Get-GrepaiIdleTimeoutMinutes (default: 20 minutes). The grepai crash-restart supervisor running inside the launcher (###1 L1196-1414) tracks query activity. After 20 minutes without queries, the supervisor deliberately terminates the grepai watch process and exits (return) without restarting.
- Pane Impact: The grepai pane tailer (tail_grepai.ps1, generated by New-WatcherPaneScript) polls Test-GrepaiWatcherAlive every 500 ms. Once grepai is terminated, this check fails.
- Failed Healing: The pane attempts Invoke-GrepaiHealthCheck, but because the launcher supervisor has already exited, healing fails.
- Pane Termination: After 60 dead ticks (~30 seconds), the grepai pane executes exit 0, closing the terminal pane.

### Root Cause 2: Dead CIM Fallback Probe in Test-GrapheniumWatcherAlive
- Mechanism: Modules/watcher_pane_scripts.ps1 (L129-148) defines Test-GrapheniumWatcherAlive, which checks for gm.exe processes containing watch in CommandLine.
- Stale Contract: Commit a8107e24 eliminated gm watch from the architecture. Graphenium rebuilds are now executed via gm run triggered by the $gmSemJob thread job inside the launcher.
- Impact: Test-GrapheniumWatcherAlive is dead code and can never return True. The graphenium pane currently survives only because $gmWatchPid = 70208 (the launcher's own PID). If the launcher PID check fails transiently, the pane falls back to the CIM probe, fails immediately, and exits.

### Root Cause 3: Zero Grace Period on Non-Grepai Panes
- Mechanism: In Modules/watcher_pane_scripts.ps1 (L739-740), non-grepai panes (graphenium, graphify-rs, repowise) have no tick-tolerance window.
- Impact: If  evaluates to False on even a single 500 ms polling cycle (e.g. high CPU load causing Get-Process timeout or CIM probe lag), the pane executes exit 0 immediately without retry or healing.

### Root Cause 4: Cascading Heartbeat Failure Kills All Watchers
- Mechanism: Each pane writes a heartbeat stamp every 4th tick (~2 seconds) to C:\Temp\vad-watchers\panes\hb\<label>.hb. The launcher controller loop (###1 L3911-3972) checks these timestamps against $hbTimeoutSec = 8.
- Cascading Collapse: If all pane heartbeats become stale (>8 seconds) - which occurs when panes exit, during OS sleep/modern standby, or under severe process starvation - the controller concludes the Windows Terminal tab is dead, calls Stop-AllWatchers, terminates all backend processes, and exits.

## 3. Remediation Blueprint (For Implementation in MCP-Watchers)

Work should be implemented in J:\audio\MCP-Watchers under issue mcpw-qfy:

1. Persistent Grepai Pane State:
   - Update New-WatcherPaneScript so the grepai pane does not exit when idle-reaped.
   - Render [IDLE - WAITING FOR QUERIES] in the pane.
   - Continue emitting heartbeats so the controller remains active.

2. Fix Graphenium Liveness Probe:
   - Update Test-GrapheniumWatcherAlive in Modules/watcher_pane_scripts.ps1 to reflect the post-a8107e24 architecture (probe gm serve or check launcher daemon status instead of obsolete gm watch).

3. Add Grace Period to All Panes:
   - Give graphenium, graphify-rs, and repowise a dead-tick grace window (e.g. 30-60 ticks / 15-30 seconds) before executing exit 0.

4. Harden Controller Heartbeat Check:
   - Increase $hbTimeoutSec or detect system resume events to prevent killing daemons during short system freezes or sleep transitions.
